# AI 보강 도구 1단계: 밸런스 스냅샷 추출

## 목적과 범위

슬라임 유치원에서 AI가 수치를 추측하지 않고 실제 게임 데이터를 근거로 분석하도록,
Unity 메뉴 한 번으로 업그레이드 비용·효과와 슬라임 기본 생산량을 JSON으로 추출한다.
첫 단계는 데이터 추출까지다. 자동 분석 보고서, 시뮬레이션, 플레이 이벤트 수집,
설치형 AI 스킬은 이후 단계이며 이번 파일에는 구현되어 있지 않다.

검토 기준: `main`의 `48bf20484c7a83986e249ae8f7ef14255609ce40`.
원격 저장소에는 반영하지 않은 전달용 변경이다.

## 확인한 기존 구조

- `Upgrade`가 선형·고정·구간 효과, 구간별 비용 배율, 후반 전용 비용을 계산한다.
- `UpgradeSpecTableSO.asset`에는 시스템 업그레이드 5종이 있다.
- `SlimeSpecTable.asset`에는 20등급의 기본 포인트와 자동 생산 간격이 있다.
- 기존 `IAnalyticsService.LogAdEvent`는 광고 전용이다. 진행 값과 계정 식별자를
  보내지 않도록 명시되어 있으므로 플레이 텔레메트리는 별도 계약을 설계해야 한다.
- `PointCalculator`는 현재 Manager의 업그레이드·도감 상태에 의존한다.
  이번 도구는 이 함수를 호출하지 않으며 실제 계정의 생산량이라고 표시하지 않는다.

## 설치와 실행

1. ZIP의 `Assets`와 `Documentation`을 Unity 프로젝트 루트에 복사한다.
   추가 파일은 C# 스크립트, 해당 meta, 이 문서뿐이다.
2. Unity가 컴파일을 마칠 때까지 기다리고 Console의 오류를 확인한다.
3. Play Mode를 종료한다. 편집한 밸런스 에셋이 있다면 먼저 저장한다.
4. `Tools > Balance > Export Balance Snapshot`을 누른다.
5. `Builds/BalanceReports/balance-날짜-고유값.json`이 생성되고 폴더가 열린다.
6. JSON을 AI에 전달해 아래 분석 절차로 읽는다. 이 도구는 API 키나 네트워크 연결을 사용하지 않는다.

내보내기는 지정한 두 에셋 경로를 읽는다. GameScene의 Manager가 실제로 이 에셋을
참조하는지는 별도로 Inspector에서 확인한다. 씬의 등장 간격·최대 인원·오프라인
효율 같은 설정은 아직 포함되지 않으며 완전한 게임 설정 백업이 아니다.

## 결과 필드

| 필드 | 의미 |
|---|---|
| Sources | 입력 에셋·공식 파일 경로와 SHA-256. 비교 시 입력 변경 추적 |
| UpgradeLevels | 최대 레벨에 도달하기 전의 모든 구매 단계 |
| FromLevel / ToLevel | 구매 전후 레벨. 최대 레벨에서의 추가 구매 행은 없음 |
| Cost | 실제 `Upgrade.Cost`로 계산한 이번 구매 비용 |
| CumulativeCost | 0레벨부터 ToLevel까지 해당 업그레이드만 구매한 누적 비용 |
| PointBefore / PointAfter / PointGain | 효과의 원래 단위. 초·인원·퍼센트 등을 서로 직접 비교하면 안 됨 |
| HasPreviousCost / CostRatioToPrevious | 첫 구매는 비교 대상 없음. 이후 이전 구매 대비 비용 배율 |
| Slimes.BasePointsPerSecond | 기본 Point / AutoClickInterval. 보너스 없는 슬라임 한 마리의 이론 평균 |

효과 값은 새 `Upgrade` 객체를 생성해 기존 코드로 계산한다. 실제 플레이어 레벨을
올리거나 에셋을 수정하지 않는다. 기본 생산량에는 업그레이드, 도감, 특별 슬라임,
광고 배율, 장식장 제외, 일시정지, 필드 구성 등이 반영되지 않는다.

## 사용자 확인 절차

저장소 AGENTS.md에 따라 빌드·Play Mode·기기 실행 및 도구 실행 검증은 사용자가 한다.
이번 전달물은 소스 검토 상태이며 Unity 컴파일·메뉴 실행 통과를 주장하지 않는다.

| 확인 | 통과 기준 | 실패 시 확인 |
|---|---|---|
| 컴파일 | Console 오류 없이 메뉴 표시 | 오류 전문과 Unity 버전 전달 |
| 현재 테이블 추출 | UpgradeLevels 369행, Slimes 20행 | 테이블이 변경되었는지 먼저 확인 |
| 첫 등장 시간 업그레이드 | SpawnTimeSub 0→1: Cost 100, PointBefore 0, PointAfter 약 0.1 | 입력 에셋 및 공식 확인 |
| 후반 비용 전환 | AllSlimePointPercentAdd 100→101: Cost 1000000000000 | LateCostStartLevel·LateBaseCost 확인 |
| 최대 레벨 | AllSlimePointPercentAdd 마지막 행 199→200, PointAfter 150 | 구간 공식·MaxLevel 확인 |
| 기본 생산량 | Grade 1: BasePoint 10, AutoClickInterval 5, BasePointsPerSecond 2 | 슬라임 테이블 확인 |
| 저장 안 된 에셋 | 경고가 나오고 새 보고서가 생기지 않음 | 먼저 에셋 저장 |
| 반복 내보내기 | 별도 파일 생성, 기존 JSON 유지 | 출력 폴더 쓰기 권한 확인 |
| 원본 보존 | Git에서 씬·밸런스 에셋·기존 코드 변경 없음 | 도구 외 편집 여부 확인 |

위 숫자는 검토 기준 커밋의 에셋에서 읽은 기대값이며 실행 결과가 아니다.

## AI가 결과를 읽는 절차

1. SchemaVersion, Scope, PointUnits, Sources를 확인한다.
2. 비용 증가가 큰 지점, 비용 감소 지점, 효과 증가량이 바뀌는 지점을 표로 정리한다.
3. 해당 업그레이드의 단위를 확인한다. 값만 보고 효율 순위를 단정하지 않는다.
4. 비용 곡선에서 확인한 사실과 실제 플레이에 대한 가설을 분리한다.
5. 가설을 확인하는 데 필요한 플레이 데이터 또는 시뮬레이션 조건을 제시한다.
6. 비교본이 있으면 같은 Type·SlimeGrade·FromLevel로 맞추고 변경된 행을 비교한다.
7. 수치 수정은 별도 변경으로 제안한다. 보고서 생성 자체가 밸런스를 바꾸지는 않는다.

요청 예: “이 JSON의 비용·효과 전환점을 찾아줘. 관측된 수치, 예상 영향,
확인에 필요한 플레이 데이터로 나눠서 설명해줘. 성장 시간이나 이탈률은 추측하지 마.”

## 이후 연결 순서

- 2단계: 스냅샷 비교 및 전환점 자동 보고서. 반복 분석 절차를 스킬로 정리.
- 3단계: 플레이 텔레메트리 계약과 로컬 수집. 이벤트는 성공한 행동 기준으로 기록하고,
  게임 진행 저장과 분리한다. 테스트·실제 사용자 데이터를 구별한다.
- 4단계: 가상 플레이어와 성장 시뮬레이션. 필드·행동·해금·일시정지 규칙까지 포함하고
  실제 플레이 기록과 비교해 모델의 오차를 확인한다.
- 5단계: 후보 수치별 실험, AI 해석, 개발자 검토를 반복하는 작업 흐름.

이 순서는 초기 제안이며 1단계 사용 결과에 따라 조정한다.
