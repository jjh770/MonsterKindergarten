# 탐험 구현

현재 상태와 확인 절차는 마지막 **6단계**를 기준으로 읽는다. 앞 단계는 당시 구현 기록이며
단일 탐험 제한과 1시간 임시값 등은 후속 단계에서 대체됐다. 탐험 선택·편성·수령 화면과 운영 보상까지 연결됐다. 실제 플레이·Android 검증은 사용자 확인 전이다.

## 1단계: 출발과 시간·보상 모델

2026-10-16, `codex/display-room-decorations`에서 시작했다. 기존 장식장 작업을 유지하며
탐험의 순수 도메인 모델부터 추가했다. 이 단계에서는 씬·저장·재화에 연결하지 않는다.

### 확정된 방향

- 장식장에 모은 슬라임을 편성해 일정 시간이 걸리는 탐험을 보낸다.
- 기본 보상 재화는 기존 포인트·뽑기권이다. 낮은 확률로 장식장 장식을 얻는다.
- 새 재화는 추가하지 않는다.
- 기기 타이머를 누적하지 않고 출발·도착 UTC 시각을 비교한다. 런타임 연결 시에는
  `ServerClock.TrustedUtcNow`를 전달한다.

### 구현한 타입

| 타입 | 책임 |
| --- | --- |
| `ExpeditionMember` | 출발 순간의 개체 ID·등급·특수 여부를 변경 불가능한 값으로 보관 |
| `ExpeditionReward` | 고정 포인트·뽑기권·선택적 장식 보상. 음수·비정수·비유한 포인트와 잘못된 장식 거부 |
| `ExpeditionRun` | 탐험 ID·장소 ID·편성·출발/도착 UTC·보상. 남은 시간·진행률·귀환 준비 여부 계산 |
| `ExpeditionDeparture` | 빈 편성·정원 초과·중복 개체·장식장 밖 개체를 거부하고 출발 스냅샷 생성 |

외부에서 전달한 편성 목록은 복사해 읽기 전용으로 보관한다. 출발 후 같은 목록을
수정하거나 슬라임을 꺼내도 기록된 등급·편성이 바뀌지 않는다. 이 모델은 슬라임의
실제 위치나 도감 등록을 변경하지 않으며 보상을 지급하지도 않는다.

`ExpeditionRun` 생성자는 저장 복원에도 쓸 수 있도록 현재의 편성 상한을 강제하지 않는다.
출발할 때만 현재 설정 상한을 `ExpeditionDeparture`에 전달한다. 따라서 향후 정원을
낮춰도 이미 출발한 탐험 기록을 단순히 정원 초과로 버리지 않을 수 있다.

보상 값과 장식 추첨 결과는 출발 시 고정할 수 있도록 모델에 포함했다. 귀환 UI를
다시 열 때마다 보상을 재계산하거나 장식을 다시 뽑지 않는다. 추첨기·보상량 공식은
아직 연결하지 않았다.

### 확인 중인 첫 구성

아래 정원·시간·해금은 2단계 서비스의 기본값으로 연결했다. 운영 보상 수치와 화면에는 아직 적용하지 않았다.

- 탐험대 1개, 장식장 슬라임 최대 3마리
- 기본 탐험 시간 1시간
- Lv.7 해금
- 탐험 중에도 장식장 모습과 도감 보너스 유지

포인트 산식·뽑기권 수량/주기·장식 확률·이미 가진 장식의 중복 처리도 확정이 필요하다.
현재 종류당 1개 소유 제한이 있으므로 중복 장식을 아무 안내 없이 버리는 처리는 넣지 않는다.

## 다음 단계의 책임과 저장 계획

1. 설정 에셋: 장소·시간·정원·해금·보상 수치를 관리한다.
2. SlimeStatus: 탐험 ID·편성 스냅샷·출발/도착·고정 보상·수령 진행을 소유한다.
   현재 v17에는 탐험 필드가 없으므로 추가 전에 다음 스키마 승격을 명시한다.
   이전 계정은 진행 중 탐험 없음으로 시작하고 기존 진행도는 유지한다.
3. 탐험 서비스: 출발 당시 실제 보유한 장식장 개체인지 다시 확인하고, 한 탐험대의
   중복 출발을 막으며, 신뢰 시각으로 귀환 가능 여부를 확인한다.
4. 보상 정산: 포인트와 뽑기권은 `CurrencyManager.TryApplyChanges`로 한 번에 반영한다.
   장식은 SlimeStatus 소유권으로 반영하므로 Currency와 SlimeStatus 두 문서가 참여한다.
   보상 수령 기록과 재개 절차를 설계한 뒤 연결한다. 현재의 구매 롤백 함수만으로
   앱 종료 후 중복·누락 복구가 보장된다고 취급하지 않는다.
5. UI: 하단 진입 버튼, 장소와 편성 선택, 남은 시간, 귀환 결과를 연결한다.

저장 키·UID·클라우드 컬렉션은 그대로 유지할 계획이다. 보상 정산의 수령 기록을
Currency에 추가하게 되면 해당 문서도 별도 스키마 승격 계획이 필요하다. 이번 단계는
기존 저장 스키마 2/17/1을 변경하지 않는다.

## 검증과 다음 확인

이번 단계는 에디터 컴파일과 정적 검토까지만 진행한다. 사용자 지침에 따라 자동 테스트,
Play Mode, Android 기기 검증은 실행하지 않는다. 실제 게임에서는 아직 탐험 버튼이나
진행 중 탐험이 나타나지 않는다.

후속 저장·서비스 단계에서 사용자가 확인할 항목은 다음과 같다.

- 장식장 슬라임만 정원 안에서 편성되고 같은 개체를 두 번 고를 수 없는지
- 탐험 중 재접속해도 같은 편성·도착 시각·보상이 복원되는지
- 도착 시각 직전에는 수령할 수 없고, 도착 시각부터 귀환 대기가 되는지
- 이미 보유한 장식의 처리 결과와 표시가 일치하는지
- 수령 중 앱 종료 후 재접속해 재화·장식이 중복되거나 누락되지 않는지

## 2단계: 저장과 귀환 정산 서비스 (복수 탐험 요구 이전 구현)

### 현재 구현 상태

- `ExpeditionService`가 출발, 귀환 수령, 미완료 정산 복구를 담당한다.
- 기본 정원 3마리·시간 1시간이다. 생성자 인자로 바꿀 수 있으며 설정 에셋과 UI 연결은 다음 단계다.
- Lv.7 이상에서 실제 보유한 장식장 슬라임의 ID로만 출발한다. 탐험은 동시에 하나이며,
  수령 전에는 새 탐험을 시작하지 못한다. 슬라임 위치나 도감 효과는 바꾸지 않는다.
- 보상량·장식 추첨 결과는 호출자가 계산해 출발 시 넘긴다. 운영 보상 공식·확률은 미적용이다.
- `ExpeditionRunSaveData`가 편성·시간·보상·정산 순번을 SlimeStatus에 기록한다.
- 자동 복구 호출이나 게임 버튼은 아직 없다. 다음 UI 단계에서 서비스 생성 후 플레이 가능 상태에
  `TryRecoverSettlement`를 호출하고, 출발·수령도 같은 서비스를 거치게 연결해야 한다.

### 보상 복구 순서

각 문서에 순번, 누적 포인트, 누적 뽑기권, 획득 장식 비트 목록을 저장한다.

1. 귀환 수령 시 SlimeStatus에서 탐험을 완료하고 누적 보상·장식 소유권을 함께 저장한다.
2. Currency는 누적 지급 기록과 비교해 아직 반영하지 않은 포인트·뽑기권 차이만 더한다.
   잔액과 지급 기록은 한 번에 저장하며, 기록을 갱신한 뒤 UI 이벤트를 발행한다.
3. 종료·재접속 등으로 두 문서의 순번이 다르면 앞선 누적 기록으로 뒤쪽을 맞춘다.
   Currency가 앞서면 SlimeStatus의 완료 순번·장식도 복원하고 오래된 탐험을 제거한다.
4. 같은 순번의 내용이 다르거나 누적값이 줄어드는 등 일관성이 없으면 서비스는 실패한다.
   임의로 보상을 다시 지급하거나 정상 문서를 초기화하지 않는다.

이것은 단일 진행 흐름에서 문서 저장 순서 차이를 복구하기 위한 방식이다. 서로 다른 기기가
동시에 독립적으로 진행한 충돌을 서버에서 병합하거나, 두 Firestore 문서를 트랜잭션으로
함께 확정하는 구현은 아니다. 실제 종료·재접속 및 클라우드 시차 복구는 아직 검증 전이다.

### 적용한 마이그레이션

현재 스키마는 Currency 3 / SlimeStatus 18 / Upgrade 1이다.

- SlimeStatus v17 이하는 기존 승격 경로에서 탐험 누적 기록 0을 채운다. 진행 중 탐험은 없다.
- Currency v2 이하는 기존 잔액을 유지하고 누적 지급 기록을 0으로 읽는다.
- 현재 버전 문서에 필수 누적 기록이 빠졌거나 값이 손상되면 기본값으로 덮지 않고 로드를 차단한다.
- 새 로컬 Currency 저장은 `{userId}_Currency_Document` JSON 문서다. 기존 개별 재화 키와
  시각 키는 읽기 호환용으로 보존하며, 새 문서가 없을 때만 읽는다.
- 새 문서는 잔액·지급 기록·시각·스키마를 함께 담는다. 기존 Currency 버전 표식도 최소 3으로
  올려 구버전이 오래된 개별 키로 진행하지 못하게 한다. 미래 버전 표식은 먼저 거부한다.
- 삭제는 새 문서와 이전 키를 함께 지운다. UID, 클라우드 컬렉션, Firestore 규칙은 바꾸지 않았다.
- 새 문서가 손상됐을 때 오래된 개별 키로 조용히 되돌리지 않는다. 기존 HybridRepository의
  읽을 수 있는 클라우드 문서 복구 경로는 그대로 유지한다.

### 사용자가 실행할 로컬 확인 절차

에이전트는 아래 메뉴와 Play Mode를 실행하지 않았다. 메뉴는 Editor 전용이며 실행하면
LocalPlayer의 저장과 실제 로컬 잔액이 바뀐다. 이전 저장 복사본은 검증 전에 보존한다.

1. LoginScene에서 플레이하고 Lv.7 이상·장식장 슬라임 1마리 이상 상태를 준비한다.
2. `Tools > Expeditions > Start Local Test (10 seconds)`를 누른다. 최대 3마리를 편성하고,
   포인트 100·뽑기권 1·랜턴 보상을 고정한 10초짜리 로컬 테스트 탐험이 시작되어야 한다.
   이 수치는 검증용이며 운영 보상 설정이 아니다.
3. 바로 같은 출발 메뉴를 다시 누르면 출발하지 못해야 한다. 10초 전 수령 메뉴도 지급하면 안 된다.
4. 출발 후 플레이를 종료하고 다시 시작해도 출발 메뉴를 재실행하지 않은 채
   `Claim Local Test Reward`로 기존 탐험을 수령할 수 있어야 한다.
5. 10초 이후 수령하면 포인트 100·뽑기권 1이 한 번만 추가되고 랜턴이 소유 상태가 되어야 한다.
   이미 가진 랜턴은 종류당 1개 제한 때문에 수가 늘지 않는다. 검증 메뉴에는 중복 보상 환산이 없다.
6. 수령 메뉴와 `Recover Local Settlement`를 반복해도 재화가 더 늘지 않아야 한다.
7. 같은 계정의 문서 복사본으로 SlimeStatus 순번이 앞선 경우와 Currency 순번이 앞선 경우를
   각각 준비해 복구 메뉴를 실행한다. 뒤쪽만 따라오고 포인트·뽑기권·장식이 중복되면 안 된다.
   실제 사용자 클라우드 문서는 이 확인을 위해 지우거나 임의 수정하지 않는다.
8. 신규 저장, v2/v17 저장의 승격, 새 로컬 문서 손상, 미래 스키마 거부, 계정 삭제 후 신규 진입도
   확인한다. 클라우드 저장·복원은 별도 Android 검증 항목이다.

최종 자동 확인은 Unity 컴파일과 `git diff --check`까지다. 실제 수령·재접속·복구 성공을
확인했다고 보고하지 않는다.

## 3단계: 탐험지별 시간·편성 규칙

### 확정 요구

- 탐험지는 3종이며 소요 시간은 각각 2시간, 4시간, 8시간이다.
- 서로 다른 탐험지에 탐험대를 동시에 보낼 수 있다. 탐험대당 최대 3마리다.
- 탐험지마다 필요한 슬라임 종류가 다르다. 같은 개체를 다른 팀에 중복 편성할 수 없다.
- 파견 중에는 장식장에서 숨기고 Lv.7부터 탐험을 해금한다.
- 구체적인 필요 등급 조합, 보상량·장식 확률은 아직 확정하지 않았다.

### 이번에 적용한 범위

`ExpeditionDestination`은 세 탐험지의 고정 ID와 2·4·8시간을 정의한다. 필요 등급은
생성 시 별도로 전달하며 1~3종의 서로 다른 유효 등급만 허용한다. 운영 조합을 임의로
확정하지 않는다. 일반·특별 슬라임은 같은 등급이면 같은 종류로 인정한다.

`ExpeditionDeparture`의 탐험지 기반 출발 경로는 기존 개체 중복·장식장 소속·정원 검증에
더해 필요 등급 충족 여부를 확인하고, 해당 탐험지의 시간으로 귀환 시각을 계산한다.
필요 종류를 모두 갖췄다면 정원 내 추가 편성은 허용한다. 기존 출발 API와 10초 검증
메뉴는 유지한다. 이번 단계는 저장 스키마 3/18/1을 변경하지 않는다.

### 다음 단계와 제한

현재 `ExpeditionService`와 저장 문서는 여전히 단일 탐험 구조다. 새 탐험지 규칙은 아직
서비스·UI에 연결하지 않았다. 복수 팀 파견, 파견 중 숨김, 중복 편성 금지는 아직 미적용이다.
1시간 기본값은 기존 서비스의 임시값이며 확정된 운영 시간이 아니다.

다음 저장 단계에서는 활성 탐험 목록, 탐험지별 점유, 개체 중복 편성 차단, 귀환 순서와
무관한 정산·복구를 함께 설계한다. 기존 전역 순번 비교로 활성 탐험을 제거하면 나중에
출발한 짧은 탐험이 먼저 돌아올 때 다른 팀까지 지워질 수 있으므로 그대로 확장하지 않는다.
v18의 단일 탐험을 새 목록으로 보존하는 승격 계획을 먼저 명시한다. 장식장 숨김은 저장된
활성 편성을 기준으로 복원하며 저장 위치를 임의로 바꾸지 않는 방향으로 진행한다.

### 사용자 확인 항목

Unity에서 컴파일 오류가 없는지 확인한다. 이후 서비스 연결 단계에서 2·4·8시간 표시,
필요 종류 부족 시 출발 차단, 세 팀 동시 진행, 동일 개체 중복 편성 차단, 역순 귀환 수령,
재접속 복원과 파견 슬라임 숨김을 각각 확인한다. 이번 단계만으로 해당 게임 동작이
구현되거나 검증됐다고 보지 않는다.


## 4단계: 복수 탐험 저장·정산

### 적용 범위

- 활성 탐험은 최대 3개이고 같은 탐험지는 한 팀만 점유한다. 각 팀은 최대 3마리다.
- 파견 개체 ID는 다른 팀에서 쓸 수 없고, 이동·합성도 도메인에서 거부한다.
- 탐험지 규칙을 받는 서비스 출발 경로를 추가했다. 해당 경로는 필요 등급을 확인하고
  2·4·8시간을 적용한다. 구체적인 등급 조합과 운영 보상은 여전히 미확정이다.
- 수령은 RunId로 지정한다. 출발 순서와 수령 순서를 분리하고, 누적 지급 기록에
  탐험지별 마지막 완료 출발 순번을 함께 보존한다. 다른 탐험지의 높은 순번이
  미수령 팀을 제거하지 않는다. 같은 탐험지의 옛 저장이 돌아오면 완료 기록으로 제거한다.
- 지급 순번이 같은데 내용이 다른 기록은 기존과 같이 거부한다. 두 기기의 독립 진행을
  병합하는 서버 트랜잭션은 아니다. 자동 시작 복구 호출·숨김·게임 UI는 다음 단계다.

### 마이그레이션 계획과 구현

현재 스키마는 Currency 4 / SlimeStatus 19 / Upgrade 1이다.

1. Currency v3의 누적 지급 순번·포인트·뽑기권·장식을 유지하고, 기존 순번을
   LegacyCompletedSequence로 보존한다. 탐험지별 완료 사전은 빈 상태로 시작한다.
   v2 이하는 기존 잔액을 유지하고 빈 정산 기록으로 읽는다.
2. SlimeStatus v18의 단일 탐험을 ActiveExpeditions 목록으로 옮긴다. RunId, 목적지,
   출발 순번, 편성, 출발·귀환 시각, 보상을 바꾸지 않는다. 기존 누적 기록도 같은 방식으로
   승격한다. v17 이하는 진행 중 탐험 없음·누적 0을 거쳐 새 형식으로 올라온다.
3. 새 SlimeStatus 저장은 단일 필드를 null로 쓰고 목록만 기록한다. 새 버전에 목록이나
   완료 사전이 없으면 결손으로 거부하며, 이전 버전에서만 명시적으로 채운다.
4. 구버전 앱은 새 문서를 상위 버전으로 거부한다. 로컬 Currency 버전 표식도 현재
   버전 이상으로 기록한다. 기존 키·컬렉션·UID는 유지하고 플레이어 문서는 삭제하지 않는다.
5. 기존 누적 정산의 시차도 복구할 수 있게 이전 완료 기준을 보존한다. 새 출발 순번은
   기존 완료 기준, 탐험지별 완료 순번, 활성 탐험 순번보다 항상 크게 할당한다.

### 사용자가 실행할 확인 절차 (이전 10초 단일 탐험 절차를 대체)

아래 메뉴는 실제 LocalPlayer 저장과 재화를 바꾼다. 기존 저장 복사본을 보존한다.
에이전트는 Play Mode·메뉴 실행·기기 테스트를 하지 않는다.

1. LoginScene에서 플레이하고 Lv.7 이상, 파견하지 않은 장식장 슬라임 3마리를 준비한다.
2. Tools > Expeditions에서 30 seconds, 20 seconds, 10 seconds 출발 메뉴를 순서대로
   실행한다. 메뉴는 각각 다른 탐험지에 남은 개체 1마리씩 보내며 운영 시간과 별개다.
3. 같은 출발 메뉴를 다시 실행하면 실패해야 한다. 각 탐험지당 한 팀만 진행해야 한다.
4. 짧은 탐험의 출발 후 10초가 지나면 Claim Local Test Reward를 실행한다.
   준비된 탐험 중 마지막으로 출발한 팀을 수령하므로, 먼저 출발한 30초 팀이 남아야 한다.
   각 수령 로그에는 탐험지와 남은 팀 수가 표시된다. 기다린 시간에 따라 다른 팀도
   도착했더라도 한 번 누를 때 한 팀만 처리한다.
5. 각 팀의 보상은 포인트 100·뽑기권 1·랜턴이며 세 팀을 수령하면 합계 300·3이다.
   랜턴은 기존 종류당 1개 제한을 유지한다. 이미 가진 장식에 대한 환산은 검증 메뉴에 없다.
   수령과 Recover Local Settlement를 반복해도 더 지급되면 안 된다.
6. 팀이 남아 있을 때 플레이를 종료하고 다시 들어온다. 출발 메뉴를 누르지 않아도
   기존 시각에 맞춰 수령할 수 있어야 한다. 도착 전에는 지급되면 안 된다.
7. 수령한 탐험지만 다시 출발할 수 있어야 하고 아직 진행 중인 다른 팀은 유지돼야 한다.
8. 신규 저장, v3/v18 단일 탐험 저장의 승격, Currency/SlimeStatus 정산 시차 양방향,
   필수 목록·사전 결손 차단, 상위 버전 거부는 보존한 검증용 문서로 따로 확인한다.
   실제 사용자 클라우드 문서를 지우거나 임의 수정하지 않는다. Android 복원은 별도 확인한다.

장식장에서 숨기는 표현은 아직 연결하지 않았으므로 이번 단계에서는 파견 슬라임이
보일 수 있다. 다만 이동과 합성은 거부한다. 숨김·선택 차단·귀환 표시가 연결된 뒤에
해당 화면 동작을 검증한다. 현재 게임에 탐험 진입 버튼은 없다.


## 5단계: 파견 슬라임의 장식장 숨김과 귀환 표시

### 적용 범위

- GameplaySpaceManager가 파견·수령·정산 복구 이벤트를 받아 장식장 가시성을 갱신한다.
  출발한 팀만 숨고 수령한 팀만 다시 나타난다. 도착 예정 시각이 지나도 수령 전에는 숨긴다.
- 첫 복원, 공간 이동, 슬라임 생성의 기존 표시 경로에서도 파견 여부를 판정한다.
  장식장을 나갔다 들어오거나 재접속해도 수령 전 개체는 계속 숨는다.
- 기존 SetLocationPresentationActive 경로로 그림·콜라이더·물리·이동을 함께 끈다.
  직접 호출되는 놀이터 대상 판정에도 가시성을 확인해 숨은 개체는 반응하지 않는다.
- 저장 위치는 DisplayRoom으로 유지한다. 도감 등록과 보관 자리는 보존하고, 같은 등급의
  추가 보관은 기존 제한을 따른다. 장식장 슬라임은 원래 자동·오프라인 생산 대상이 아니므로
  파견 중에도 생산하지 않는다. 도감의 특별 모습 판정도 기존 장식장 보관 규칙을 유지한다.
- 숨겨진 개체는 정보창을 새로 열 수 없다. 이미 열어 둔 개체를 Editor 메뉴로 파견하면
  정보창·관찰·입력 소유권을 정리하고 카메라를 기본 장식장 화면으로 되돌린다.
- 탐험 이벤트는 실제 가시성이 바뀐 장식장 개체만 갱신한다. 다른 개체의 대포 숨김이나
  메인 필드 뽑기 연출의 그림 상태를 일괄 덮어쓰지 않는다.

저장 스키마는 4/19/1을 유지한다. 씬 참조나 저장 필드는 추가하지 않았다.
게임용 탐험 선택 화면, 운영 편성 조합과 보상 설정, 자동 정산 복구 호출은 여전히 미연결이다.

### 사용자가 실행할 확인 절차

에이전트는 Play Mode·로컬 검증 메뉴·기기 테스트를 실행하지 않는다.
메뉴는 실제 LocalPlayer 저장을 바꾸므로 저장 복사본을 보존한다.

1. LoginScene에서 플레이하고 Lv.7 이상, 장식장 슬라임 3마리 이상을 준비한다.
   장식장 화면에서 Tools > Expeditions의 10·20·30 seconds 출발 메뉴를 각각 실행한다.
   메뉴당 1마리씩 숨고 남은 슬라임은 계속 돌아다녀야 한다.
2. 숨은 자리에서 탭해도 그 개체의 정보창이 열리거나, 범퍼·대포·랜턴이 그 개체와
   상호작용하면 안 된다. 메인 필드의 기존 슬라임은 그대로 보여야 한다.
3. 장식장을 나갔다 다시 들어와도 파견 개체는 없어야 한다. 플레이를 종료하고 재진입해도
   같다. 저장에는 기존 개체 ID와 편성·귀환 시각이 남아 있어야 한다.
4. 도착 시각이 지난 뒤 Claim Local Test Reward를 한 번 실행하면 해당 팀만 다시 나타나고,
   남은 파견 팀은 계속 숨겨져야 한다. 귀환한 슬라임은 다시 이동·선택·놀이터 반응이 가능해야 한다.
5. 대기 슬라임의 정보창 또는 관찰 화면을 연 채 출발 메뉴를 실행한다. 메뉴가 해당 개체를
   선택했으면 화면이 닫히고 카메라가 기본 보기로 돌아와야 한다. 돌아온 뒤 다른 슬라임 선택과
   뒤로가기가 가능해야 하며 입력이 잠긴 채 남으면 실패다.
6. 가능하면 파견 대상과 다른 슬라임이 대포에 잡혀 있을 때 출발·수령한다. 그 슬라임의
   대포 연출이 중간에 드러나거나 초기화되지 않아야 한다. 메인 필드 뽑기 연출도 별도로 확인한다.

Unity 컴파일과 정적 검사는 게임 동작 확인과 구분한다. Android 재접속·클라우드 복원은
Editor 로컬 확인과 별도로 검증한다.


## 6단계: 게임 화면과 운영 보상

### 확정된 규칙

| 탐험지 | 시간 | 해금 | 뽑기권 | 장식 발견 확률 |
| --- | --- | --- | --- | --- |
| 꽃밭 산책 | 2시간 | Lv.7 뽑기 해금 | 1장 | 3% |
| 숲속 소풍 | 4시간 | Lv.7 + 일반 도감 10종 등록 | 2장 | 6% |
| 별빛 여행 | 8시간 | Lv.7 + 일반 도감 13종 등록 | 4장 | 12% |

각 탐험은 최고 해금 레벨 이하의 장식장 슬라임 중 서로 다른 3종을 자유 편성한다.
일반·특별은 같은 등급이면 같은 종류다. 이전 고정 등급 조합 제안은 적용하지 않는다.
파견 개체는 다른 팀과 공유할 수 없다. 같은 탐험지에는 한 팀만 보낸다.

포인트는 출발할 때 편성한 각 슬라임의 자동 생산 1회 포인트에
floor(탐험 시간 / 자동 생산 간격)을 곱한 합이다. 자동 생산량 100%를 기준으로 하며,
PointCalculator를 통해 업그레이드·도감·특별 3배를 포함하고 광고 부스트는 제외한다.
출발 후 업그레이드가 바뀌어도 저장된 보상은 달라지지 않는다.

장식 발견 판정을 통과하면 4종 중 하나를 같은 확률로 선택한다. 기존 종류당 1개 제한을
유지하며 이미 가진 장식은 수량이 늘거나 다른 재화로 환산되지 않는다. 이 점을 화면에 알린다.

### 화면 연결

- 기존 장식장 하단 가로 스크롤 메뉴에 탐험 버튼을 추가했다. Lv.7 이전과 메인 필드에서는 숨긴다.
- ExpeditionUI는 별도 모달 캔버스(정렬 50)로 열리고 기존 GameplayModeSession을 통해
  HUD·상점·월드 입력·뒤로가기 소유권을 관리한다. 닫기와 뒤로가기로 자기 소유권만 해제한다.
- 세 탐험지 탭에서 해금 조건·도감 등록 수·편성·보상 미리보기·남은 시간·수령 상태를 표시한다.
- 장식장 슬라임은 20개 등급 카드의 가로 스크롤에서 선택한다. 미보유·파견·연출 중 개체는
  선택하지 못한다. 3종이 채워져야 출발할 수 있다. 최고 해금 레벨 검사는 서비스에도 적용했다.
- 기존 저장에 같은 등급의 일반·특별이 함께 남은 경우 선택 중 개체를 우선하고, 그렇지 않으면
  파견 가능한 개체를 우선 표시한다. 같은 등급 둘을 한 팀에 넣지는 않는다.
- GameplayGate 준비 후 한 번, 화면을 열 때, 출발·수령 전에 누적 정산 복구를 시도한다.
  복구가 실패하면 해당 화면에서 출발·수령을 막고 다시 열어 재시도할 수 있게 안내한다.
- 이전 단일 테스트 목적지처럼 현재 세 탐험지 ID에 없는 저장은 짧은 탐험 카드에서 수령한다.
- 카메라 확대 중 열면 기본 보기로 복귀한 뒤 화면을 연다. 정보·관찰 화면이 열렸거나
  튜토리얼·공간 전환 중이면 진입하지 않는다. 튜토리얼 시작·공간 이탈 시 화면을 닫는다.

운영 보상 계산은 ExpeditionRewardCalculator, 출발·수령 정산은 ExpeditionService,
표시는 ExpeditionUI가 맡는다. 새 저장 필드는 없으며 스키마 4/19/1을 유지한다.

### 사용자가 확인할 절차

에이전트는 Play Mode·출발·수령·Android 테스트를 실행하지 않았다. 정적인 Editor 화면
미리보기와 직렬화 참조 확인은 실제 입력·저장·재접속 검증을 대신하지 않는다.

1. LoginScene에서 시작한다. Lv.7 이전에는 탐험 버튼이 없어야 하고, Lv.7 이후 장식장 하단
   메뉴를 좌우로 밀면 탐험 버튼이 보여야 한다. 메인 필드에서는 숨겨져야 한다.
2. 탐험 버튼으로 화면을 연다. 뒤의 슬라임·상점·HUD에 입력이 전달되지 않아야 한다.
   닫기와 Android 뒤로가기로 나와서 장식장 선택·이동을 계속할 수 있어야 한다.
3. 도감 9종 이하에서 4·8시간은 잠기고 조건·현재 수를 보여야 한다. 10종이면 4시간,
   13종이면 8시간이 열려야 한다. 잠긴 탭을 눌러 조건을 읽을 수는 있지만 출발은 안 된다.
4. 자유로운 3종을 선택한다. 1~2종만 고르면 출발 버튼이 비활성이고 3종에서 활성이어야 한다.
   선택 해제와 재선택이 가능하고 네 번째를 누르면 정원 안내가 나와야 한다.
   가로 드래그 도중 카드가 잘못 선택되면 실패다.
5. 출발 전 포인트·뽑기권·장식 확률을 확인한다. 출발 시 해당 3마리가 장식장에서 숨고
   시간은 해당 탐험지의 2·4·8시간으로 시작해야 한다. 같은 개체는 다른 팀에서 고르지 못해야 한다.
6. 세 탐험지에 별도 3종씩 파견할 수 있어야 한다. 돌아온 팀을 수령할 때 다른 팀은 남고,
   보상과 복귀는 해당 팀에만 적용돼야 한다. 실제 시간 검증은 운영 2·4·8시간을 따른다.
7. 짧은 수령 확인은 기존 Tools > Expeditions의 10·20·30초 메뉴로 별도 로컬 저장에서 진행할 수
   있다. 이 메뉴는 운영 편성·시간·보상과 다른 1마리 검증 경로이며, 해당 탐험지 탭에서 수령한다.
   운영 편성 조건을 검증한 것으로 취급하지 않는다. 반복 수령으로 뽑기권이 더 늘면 안 된다.
8. 출발 후 종료·재접속해 기존 편성과 귀환 시각이 남고, 수령 이후에도 재접속해 지급이
   중복되지 않아야 한다. 보상 포인트와 별개로 메인 필드 자동 생산은 계속될 수 있다.
9. 화면을 연 채 튜토리얼이 시작되는 경우, 정보·관찰·배치·뽑기 등 다른 모달과의 입력,
   작은 세로 화면과 넓은 화면의 글자·스크롤·버튼 배치를 확인한다.
10. Android에서는 뒤로가기·백그라운드 복귀·서버 시각·클라우드 복원을 따로 확인한다.
