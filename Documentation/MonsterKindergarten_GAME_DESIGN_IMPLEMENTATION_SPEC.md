# Monster Kindergarten — Game Design & Implementation Spec

> 목적: Claude Code / Codex가 현재 Unity 프로젝트를 분석한 뒤, 아래 **확정 기획**을 기준으로 기능을 구현할 수 있도록 정리한 개발 스펙.
>
> 우선순위 원칙:
> 1. 이 문서에서 **확정**으로 적힌 규칙은 임의로 변경하지 않는다.
> 2. 기존 프로젝트 구조와 저장 구조를 먼저 분석하고, 가능한 한 기존 코드를 보존하면서 확장한다.
> 3. 수치가 `미확정`인 부분은 임의로 최종 확정하지 말고 데이터/상수로 분리해 조정 가능하게 구현한다.
> 4. 한 번에 전체 시스템을 구현하지 말고 **개발 우선순위** 순서대로 작은 단위로 진행한다.
> 5. 기존 세이브 데이터가 있다면 신규 필드 추가 시 마이그레이션/기본값을 고려한다.

# 1. 게임 정체성

> 2026-08-28 구현 상태: Phase 1·1.5, Phase 2·2-B 및 Phase 3 구현 완료. 다음은 Phase 4 가챠권.
> 현재 기준 브랜치는 `main`, 릴리스 프로필은 `0.1.07 / Code 8`,
> 개발 프로필은 `0.1.03 / Code 4`다. 로컬 AAB 생성과 기기 검증·스토어 배포 완료는
> 별개이며 후속 변경은 부록 E·F에 기록한다. 가챠·특별 슬라임 등 후속 Phase의
> 기획은 구현 완료 목록이 아니다.

## 핵심 장르

**방치형 머지 + 수집**

전투/스테이지 클리어 중심 RPG로 확장하지 않는다.

게임의 핵심 감정은 다음 세 가지다.

- 같은 슬라임을 합쳐 다음 모습의 슬라임을 발견하는 재미
- 20종의 일반 슬라임을 장식장과 도감에 모으는 재미
- 존재 자체가 숨겨진 `특별한 슬라임`을 우연히 발견하고 수집하는 재미

## 핵심 루프

```text
슬라임 자동 생성
→ 슬라임 터치 / 자동 생산으로 포인트 획득
→ 생산 및 유치원 업그레이드
→ 같은 레벨 슬라임 2마리 합성
→ 상위 레벨 슬라임 발견
→ 장식장에 직접 보관
→ 도감 등록
→ 더 높은 레벨 / 도감 완성 목표
```

보조 수집 루프:

```text
필드의 슬라임
→ 낮은 확률로 가챠권 드랍
→ 가챠권 사용
→ 특별한 슬라임 여부 우선 판정
   ├─ 실패: 일반 성장 가챠
   └─ 성공: 특별한 슬라임 가챠
→ 결과 슬라임이 메인 스테이지에 실제 생성
→ 필요하면 장식장에 직접 보관
→ 도감 등록
```

# 2. 슬라임 등급 / 합성 규칙

## 등급

- 현재 최종 등급: **Lv.20**
- 같은 레벨 2마리만 합성 가능
- 합성 비용 없음
- Lv.20은 현재 최종 단계이므로 추가 합성 불가

```text
Lv.1 + Lv.1 → Lv.2
Lv.2 + Lv.2 → Lv.3
...
Lv.19 + Lv.19 → Lv.20
```

## 최고 해금 레벨

`최고 해금 레벨`은 플레이어가 **합성을 통해 도달한 최고 일반 슬라임 레벨**을 기준으로 관리한다.

가챠는 최고 해금 레벨을 초과하는 일반 슬라임을 생성하지 않는다.

## 특별 슬라임의 수동 합성

특별 슬라임도 플레이어가 직접 드래그하면 일반 슬라임과 동일하게 합성 가능하다.

```text
일반 Lv.8 + 특별 Lv.8 → 일반 Lv.9
특별 Lv.8 + 특별 Lv.8 → 일반 Lv.9
```

- 결과는 항상 **다음 레벨의 일반 슬라임**
- 특별 속성 계승 없음
- 특별 추가 보너스 없음
- 특별 전용 합성 연출 없음
- 단, **자동 합성에서는 특별 슬라임을 완전히 제외**

# 3. 자연 스폰 시스템

## 자연 스폰 상한 — 확정

| 최고 해금 레벨 | 자연 스폰 가능 상한 |
|---|---:|
| Lv.1~4 | Lv.1 |
| Lv.5~7 | Lv.2 |
| Lv.8~10 | Lv.3 |
| Lv.11~12 | Lv.4 |
| Lv.13~15 | Lv.5 |
| Lv.16~20 | Lv.6 |

최종 자연 스폰 상한은 **Lv.6**이다.

## 스폰 확률

각 레벨의 확률을 직접 고정 %로 저장하기보다 **Weight 방식**으로 관리한다.

원칙:

- Lv.1은 가장 높은 기본 Weight
- 높은 자연 스폰 레벨일수록 기본 Weight 감소
- 새 자연 스폰 레벨이 해금되면 해당 레벨의 기본 Weight를 풀에 추가
- 기존 확률을 직접 다시 계산하지 않고 전체 Weight 합으로 확률 산출

현재 1차 기본 Weight는 Lv.1부터 `1000 / 300 / 100 / 30 / 10 / 3`으로
확정했다. 밸런스 테스트에 따라 에셋 값은 조정할 수 있다.

자연 스폰 상한표와 기본 Weight는 **둘 다 ScriptableObject로 분리**한다. 후반 성장 속도는 밸런스 단계에서 조정하기로 했으므로, 상한 Lv.6과 Weight를 코드 수정 없이 바꿀 수 있어야 한다.

## 상위 슬라임 등장 확률 업그레이드

- 최고 **Lv.5 최초 달성 시 해금**
- 최대 **Lv.50**
- Lv.1에는 영향을 주지 않음
- 높은 레벨일수록 업그레이드 효과를 더 크게 받는 구조
- 새로운 자연 스폰 레벨이 열리면 기존에 투자한 업그레이드 효과를 즉시 적용
- 최종 단계에서도 Lv.6만 계속 생성되는 구조가 되지 않도록 제한

업그레이드 Lv.11 / 21 / 31 / 41에서 각각 자연 스폰 Lv.3 / 4 / 5 / 6
구간이 열린다. 실제 스폰 상한은 `최고 해금 레벨 상한`과
`업그레이드 레벨 상한` 중 낮은 값이다.

현재 1차 최대 Weight는 Lv.1부터 `1000 / 2000 / 3000 / 5000 / 5000 /
4000`이며, Lv.1 Weight는 업그레이드로 증가하지 않는다. 구간별 증가량과
Weight는 모두 `SpawnWeightTable`에서 조정한다.

현재 1차 비용은 `5000 × 1.25^현재레벨 × 2^(현재레벨 / 10의 몫)`이다.

# 4. 포인트 / 업그레이드

## 4.1 슬라임별 생산 업그레이드

각 슬라임 레벨마다 다음 두 업그레이드를 **별도로 유지**한다.

- 터치 생산
- 자동 생산

둘 다 **무한 업그레이드**.

UI는 40개를 평면적으로 나열하지 말고 **슬라임별 카드 안에 두 업그레이드를 묶어서 표시**한다.

```text
버섯 슬라임 / No.12

터치 생산 Lv.27
현재 값 → 다음 값
[강화]

자동 생산 Lv.31
현재 값 → 다음 값
[강화]
```

생산 업그레이드의 정확한 효과 증가율/가격 공식은 **밸런스 단계에서 확정**한다.

## 4.2 업그레이드 UI 카테고리

권장 구조:

```text
[슬라임] [유치원]
```

### 슬라임

- 각 슬라임의 터치 생산
- 각 슬라임의 자동 생산

### 유치원

- 생성 속도
- 최대 슬라임 수
- 상위 슬라임 등장 확률
- 자동 합성 관련 업그레이드(해금 이후)
- 자동 스폰 ON / OFF (해금 이후, §5.1)

# 5. 슬라임 생성 속도

## 확정 수치

- 기본 생성 주기: **10초**
- 업그레이드 1회: **-0.1초**
- 최소 생성 주기: **3초**
- 최대 업그레이드: **Lv.70**

```text
10.0초
9.9초
9.8초
...
3.0초 → MAX
```

## 비용 구조

- 매 레벨 가격 증가
- **10레벨마다**, 즉 생성 시간이 1초 단위로 감소하는 구간마다 비용 티어를 크게 올림
- 현재 1차 비용은 `100 × 1.18^현재레벨 × 1.5^(현재레벨 / 10의 몫)`
- 비용 값은 업그레이드 에셋에서 조정 가능하게 유지

```text
Lv.0~10   : 10초 → 9초
Lv.11~20  : 8.9초 → 8초
...
Lv.61~70  : 3.9초 → 3초
```

초반 10초가 지나치게 느린 경우 시스템 자체를 바꾸기보다 초반 비용/초기 배치로 템포를 조절한다.

## 5.1 자동 스폰 ON / OFF — 확정

플레이어가 자연 스폰을 직접 멈출 수 있다.

```text
자동 스폰 [ON / OFF]
```

- 기본값 ON
- ON / OFF 상태를 저장한다
- OFF면 스폰 타이머를 멈춘다. 다시 ON으로 바꾸면 멈춘 지점부터 이어간다
- 이미 필드에 있는 슬라임에는 영향이 없다

### 도입 이유

방치형이라 필드는 최대 개체 수까지 차 있는 상태가 정상이다. 그런데 가챠는 **메인 스테이지에 빈 슬롯이 있어야** 사용할 수 있다(§11.2). 자동 스폰을 켜둔 채로는 슬롯을 비워도 곧바로 다시 채워지므로, 티켓을 쓰려면 매번 스폰과 경쟁해야 한다.

자동 스폰을 끄면 합성으로 만든 빈 슬롯이 유지되어 티켓을 원하는 만큼 쓸 수 있다.

### 해금 시점

가챠 해금(최고 Lv.7)과 함께 연다. 이 기능의 목적이 가챠용 슬롯 확보이기 때문이고, 초반에 노출하면 스폰을 끈 채 진행이 멈추는 실수를 유도할 수 있다.

> 이 해금 시점은 목적에서 도출한 판단이다. 처음부터 열어두는 편이 낫다고 보면 바꿔도 된다.

# 6. 최대 슬라임 수

## 확정

- 게임 시작 최대 개체 수: **10마리**
- 기본 업그레이드 가능 상한: **30마리**
- 업그레이드 1회당 최대 개체 수 **+1**
- 최고 Lv.11 슬라임 최초 해금 시 **스테이지 2 해금**
- 스테이지 2 해금 후 최대 개체 수 업그레이드 31~50 구간 개방
- 최종 최대 개체 수: **50마리**

```text
시작 10
→ 업그레이드
→ 30

Lv.11 최초 해금 / 스테이지 2 개방
→ 추가 업그레이드 가능
→ 50 MAX
```

31~50 구간은 이전보다 높은 비용 티어를 적용한다.

현재 1차 비용은 `1000 × 1.5^현재레벨 × 1.05^(현재레벨 / 5의 몫)`이며,
업그레이드 에셋에서 조정 가능하다.

# 7. 장식장

## 7.1 해금

- 최고 **Lv.3 최초 달성 시 장식장 + 도감 해금**

## 7.2 역할

장식장은 UI 인벤토리가 아니라 **실제로 수집한 슬라임이 돌아다니는 별도 공간/스테이지**다.

메인 스테이지의 실제 슬라임 개체를 플레이어가 장식장으로 이동시킨다.

### 구현 형태 — 확정

장식장은 **메인 스테이지와 같은 씬 안의 세 번째 공간**으로 구현한다.

- 별도 씬을 새로 로드하지 않는다. 현재 Ground / Sky가 쓰는 방식(같은 씬, 카메라·가시성 전환)을 그대로 확장한다.
- 진입은 레벨 조건이 아니라 **전용 버튼**으로 한다. `등급 → 스테이지` 공식은 메인 스테이지(Ground / Sky)에만 적용한다.
- 저장되는 `CurrentStage`는 지금처럼 **Ground / Sky만** 가진다. 장식장에 있는지 여부는 저장하지 않는 런타임 상태이며, 앱을 재시작하면 항상 메인 스테이지에서 시작한다.
- 슬라임의 소속 공간(`MainStage` / `DisplayRoom`)은 `CurrentStage`와 **직교하는 별도 축**이다.
- 장식장 안에서는 등급으로 공간을 나누지 않는다. Lv.1과 Lv.20이 한 공간에 함께 있는다.

이유: 매니저·오브젝트 풀·세이브 리포지토리가 모두 게임 씬에 속해 있어, 별도 씬을 로드하면 장식장에 드나들 때마다 전체 재초기화(리포지토리 재조회, 오프라인 보상 재계산, 필드 슬라임 재스폰)가 발생한다.

장식장에 들어간 슬라임:

- 메인 필드에서 제거
- 포인트 생산 X
- 합성 X
- 가챠권 드랍 X
- 메인 필드 최대 개체 수에 포함 X
- 장식장 안에서 자유롭게 돌아다님

## 7.3 보관 제한

장식장 자체에는 `슬롯 수` 개념이 없다.

각 종류별로:

- 일반 슬라임 **1마리**
- 특별한 슬라임 **1마리**

까지 보관 가능.

20종 기준 이론상 일반 20 + 특별 20까지 존재 가능하지만 `40칸 장식장` 같은 용량 UI는 제공하지 않는다.

## 7.4 장식장에 넣는 방식

기본 메인 스테이지 조작:

- 터치 = 포인트 획득
- 드래그 = 합성

이 조작과 겹치지 않도록 메인 스테이지의 하단 패널을 이동 메뉴로 전환한 뒤:

```text
[장식장으로 보내기]
```

버튼을 누르면 현재 메인 스테이지가 **장식장 이동 선택 모드**로 전환된다.
장식장에 먼저 들어가거나 다른 스테이지로 이동할 필요는 없다.

선택 모드에서는:

- 터치 포인트 획득 비활성화
- 드래그 합성 비활성화
- 슬라임 선택만 가능
- 취소 버튼 또는 뒤로가기로 종료
- 화면 테두리와 선택 안내를 표시하고 기존 상·하단 HUD를 화면 밖으로 숨김
- 이미 같은 종류/같은 타입(일반 또는 특별)이 장식장에 있으면 전송하지 않고 경고 토스트 표시

선택한 슬라임은 짧은 이동 연출 후 장식장으로 이동한다.
한 마리를 보낸 뒤에도 선택 모드는 유지되며, 다른 종류를 연속해서 보낼 수 있다.
전송 연출 중에는 추가 선택과 취소를 막는다.

## 7.5 장식장에서 꺼내기

장식장 슬라임은 다시 메인 스테이지로 꺼낼 수 있다.

단:

```text
현재 메인 필드 개체 수 >= 현재 최대 개체 수
```

이면 꺼내기 불가.

장식장에서 꺼낼 때는 슬라임이 실제로 장식장을 떠나는 짧은 연출을 제공한다.

## 7.6 즉시 회수 — 확정

장식장에 넣어 도감에 등록한 직후 곧바로 다시 꺼내는 플레이는 **의도된 동작**이다.

- 도감 등록은 §9.2대로 영구 유지된다.
- 재입장 쿨다운, 최소 체류 시간, 등록 취소 같은 제약을 두지 않는다.
- 도감을 채울지 생산력을 유지할지는 플레이어의 선택으로 남긴다.

따라서 장식장은 `모아두면 이득을 주는 창고`가 아니라 **원하는 플레이어만 꾸미는 전시 공간**이다. 이 결정의 결과로 §8 관찰 UX의 실사용 빈도가 낮을 수 있으며, 구현 우선순위에서 후순위로 둔다.

4. 슬라임 바로 아래에 최소 정보 UI 표시

소개 문구는 `SlimeSpecData.Description`으로 `SlimeSpecTable.asset`에서 등급별로

표시하지 않는 정보:

- 터치 생산량
- 자동 생산량
- 업그레이드 레벨
- 확률 정보
- 상세 경제 수치

정보 하단 버튼:

```text
[관찰하기] [장식장에서 빼기]
```

## 관찰하기

- 상단과 하단의 게임 UI가 화면 밖으로 빠지는 연출과 함께 숨겨짐
- 정보 UI와 버튼도 사라지는 연출과 함께 숨겨짐
- 화면에는 슬라임과 배경만 남음
- 카메라가 해당 슬라임을 계속 부드럽게 추적
- 슬라임은 멈추지 않고 기존 행동을 계속 수행
- 화면 아무 곳이나 터치하거나 뒤로가기를 누르면 관찰 진입 전 정보 화면으로 복귀
- 복귀할 때 상·하단 게임 UI와 정보 UI가 반대 연출로 다시 나타남
- 복귀에 사용한 첫 터치는 슬라임 선택·드래그 등 다른 게임 입력으로 전달하지 않음

목표 감성: **몰래 따라다니며 구경하는 느낌**

## 장식장에서 빼기

- 메인 스테이지 빈 슬롯 확인
- 빈자리 있으면 정보 UI 종료

- 메인 스테이지에 개체 이동
- 빈자리 없으면 이동 불가

# 9. 도감

## 9.1 위치 / 형태

- 도감은 최고 Lv.3에서 장식장과 함께 해금한다.
- 메인 스테이지와 장식장 모두에서 `CollectionButton`으로 열 수 있다.
- 펼쳐지는 화면은 **책 형태 UI**로 구성한다.
- 한 페이지에 일반 슬라임 2종을 보여주고, 항목 바로 아래의 구분된 정보 영역에 선택한 슬라임 정보를 표시한다.
- 도감이 열려 있는 동안 상·하단 HUD와 슬라임 업그레이드 버튼은 화면 밖으로 이동한다.

## 9.2 등록 조건

**슬라임을 단순히 생성한 것만으로는 등록되지 않는다.**

미등록 일반 슬라임이 장식장에 들어오면 해당 종류를 즉시 영구 등록한다.

```text
슬라임 생성
→ 아직 미등록

장식장에 실제 개체 이동
→ 도감 자동 영구 등록
```

장식장에서 다시 꺼내더라도 도감 기록은 유지된다.

따라서 최고 해금 레벨과 도감 등록 수는 서로 다를 수 있다.

- 최고 해금 레벨
- 도감에 등록한 슬라임

## 9.3 일반 카테고리

처음에는 도감 상단에 **일반 슬라임 카테고리 하나만 존재**한다.

총 20종.

미등록:

- `???`
- 어두운 실루엣 등

등록:

- 이미지
- 이름
- No.
- 간단한 소개
- 현재 터치 생산량, 자동 초당 생산량, 자연 스폰 확률
- 최초 등록일
- 자연 출현 횟수
- 합성으로 탄생한 횟수
- 유효 터치 횟수
- 누적 생산 포인트

등급별 기록은 자연 스폰 타이머, 합성 결과, 실제 포인트 지급 경로에서만
집계한다. 초기 생성·세이브 복원·에디터 단축키·오프라인 보상은 제외한다.
고빈도 터치와 자동 생산은 메모리에서 누적한 뒤 30초 주기와 앱
일시정지·종료 시점에 묶어서 저장한다.

## 9.4 특별한 슬라임 카테고리

> Phase 3에서는 특별 슬라임과 특별 도감을 구현하지 않는다.
> 아래 규칙은 Phase 5에서 특별 슬라임 생성과 함께 적용한다.

특별한 슬라임의 존재는 플레이어에게 사전에 알려주지 않는다.

첫 특별 슬라임을 가챠에서 얻어도 도감 카테고리를 즉시 열지 않는다.

**첫 특별 슬라임을 실제 장식장에 넣었을 때**, 다음에 도감을 펼치면:

1. 기존 책 UI
2. 상단 카테고리에 새로운 항목 추가 연출
3. `특별한 슬라임` 카테고리 생성
4. 해당 특별 슬라임 등록

처음부터 아래 내용을 노출하지 않는다.

- 이로치 0/20
- 특별 슬라임 0/20
- 숨겨진 슬롯
- 전체 특별 슬라임 총수

특별 카테고리가 열린 이후에도 **전체 20종이라는 총량은 명시적으로 노출하지 않는 방향**.

게임 내 명칭은 `이로치`보다 **특별한 슬라임 / 특별한 모습**을 우선한다.

# 12. 가챠권 드랍

## 확정 규칙

- Lv.7 이후 활성화
- 메인 필드의 모든 슬라임은 **레벨과 관계없이 동일한 드랍 확률**
- 드랍 판정은 스폰/자동 생산과 분리

이 값은 **1차 밸런스 값**이며 플레이 테스트로 조정 가능.

## 실제 드랍

판정 성공 시 해당 슬라임 주변에 **실제 가챠권 오브젝트** 생성.

- 플레이어가 터치해서 수집
  - 티켓은 필드 오브젝트를 직접 레이캐스트하지 않고 **별도 버튼**으로 만든다. 슬라임 터치(포인트 획득)와 입력이 겹치지 않도록 버튼 쪽이 우선순위를 가진다.
  - 슬라임 터치는 초당 여러 번 일어나는 핵심 조작이므로, 티켓이 그 위에 겹쳐도 슬라임 조작을 가리지 않아야 한다.
- 획득 전까지 **영구 유지**
- 시간 경과로 사라지지 않음
- 여러 장이 쌓여도 `xN`으로 묶지 않고 개별 오브젝트 유지
- 게임 종료/재접속 후에도 미수령 티켓 유지
- 미수령 티켓 상태 저장 필요
- 티켓이 속한 스테이지는 **드랍시킨 슬라임의 등급으로 드랍 시점에 결정하고 그대로 고정**한다. 이후 그 슬라임이 합성되어 다른 스테이지로 올라가도 이미 떨어진 티켓은 움직이지 않는다.

# 15. 특별한 슬라임

## 15.1 숨김 원칙

특별한 슬라임의 존재는 **숨겨진 수집 콘텐츠**다.

사전 공개하지 않는 것:

- 특별 슬라임 총 종류 수
- 기본 등장 확률
- 미등록 보정
- 피버 시스템
- 전체 수집 진행률

가챠 튜토리얼에서는 존재 가능성만 넌지시 암시한다.

### 숨김의 한계 — 인지하고 진행

특별 슬라임은 등급당 1종이므로 **총 20종이라는 사실은 완전히 숨길 수 없다.** 플레이어는 일반 도감이 20종인 것을 보고, 특별이 일반의 다른 모습이라는 것을 한 마리만 얻어도 알게 된다. 거기서 총량이 곧바로 추론된다.

따라서 §15.1의 목표는 `총량을 알 수 없게 만드는 것`이 아니라 **`게임이 먼저 알려주지 않는 것`** 으로 읽는다.

- 숫자, 진행률, 빈 슬롯을 **UI에 먼저 띄우지 않는다**
- 도감의 특별 카테고리는 등급순 빈칸 배열이 아니라 **등록된 것만 차례로 쌓아 보여준다**
- 미등록 자리를 `???`로 나열해 총량을 드러내지 않는다

플레이어의 추론까지 막으려 하지 않는다.

## 15.2 판정 순서

가챠권 사용 시 가장 먼저 특별 슬라임 여부를 판정한다.

```text
가챠권 사용
↓
특별 슬라임 판정
├─ 실패 → 일반 가챠(-1~-4)
└─ 성공 → 특별 슬라임 종류 판정
```

## 15.3 기본 특별 확률

- 기본: **3%**
- 일반 도감 20종 완성 전까지 기본적으로 3% 고정
- 플레이어에게 확률 표시하지 않음

## 15.4 특별 슬라임 레벨 풀

특별 슬라임 판정 성공 시:

- **현재 최고 해금 레벨 이하**만 후보
- 최고 해금 레벨 자체도 특별 슬라임으로 등장 가능
- 최고 해금 레벨을 초과하는 특별 슬라임은 절대 등장하지 않음

```text
현재 최고 해금 Lv.12

일반 가챠 → Lv.8~11
특별 가챠 → Lv.1~12
```

## 15.5 미등록 특별 슬라임 보정

특별 슬라임 판정 성공 후 종류를 선택할 때:

- 이미 특별 도감에 등록한 종류: Weight 1
- 아직 특별 도감에 등록하지 않은 종류: 진행도에 따라 Weight 증가

| 특별 도감 등록 수 | 미등록 Weight |
|---:|---:|
| 0~10종 | **2** |
| 11~15종 | **3** |
| 16~18종 | **5** |
| 19종 | **8** |

이 보정 역시 UI에 표시하지 않는다.

## 15.6 알려진 예외 — 현행 유지

Lv.20 특별 슬라임을 이미 장식장에 보관한 상태에서 같은 종류가 다시 나오면 처분 경로가 없다.

- 장식장: 종류당 1마리 제한으로 보관 불가
- 수동 합성: Lv.20은 최종 등급이라 합성 불가
- 자동 합성: 특별 슬라임 제외

이 개체는 메인 필드 슬롯 1칸을 영구히 점유한다. 발생 확률이 매우 낮아 **현행 유지**로 결정했다. 실제로 문제가 되면 `이미 장식장에 등록된 특별 종류를 특별 레벨 풀에서 제외`하는 방식으로 대응한다.

Lv.19 이하의 중복 특별 슬라임은 수동 합성으로 처분한다.

### 일반 Lv.20 누적 — 현행 유지

같은 구조가 **일반 Lv.20**에도 적용된다. 자동 합성이 Lv.19 두 마리를 계속 Lv.20으로 만들고, Lv.20은 합성 불가에 장식장도 종류당 1마리이므로 처분 경로가 없다. 한 마리당 메인 필드 슬롯 1칸이 영구히 사라지며, 줄어드는 경로는 없다.

슬롯이 줄면 가챠에 필요한 빈 슬롯(§11.2)도 함께 줄어든다.

**Lv.20까지 도달하는 난이도 자체가 높아 실제로 누적되기 어렵다고 판단해 현행 유지로 결정했다.** 문제가 되면 아래 순서로 대응한다.

1. 자동 합성 결과에서 Lv.20을 제외한다. Lv.19까지만 자동 합성하고 Lv.20은 플레이어가 원할 때 수동으로 만든다. 규칙 한 줄이라 가장 저렴하다.
2. 최종 등급에 한해 장식장 보관 수 제한을 푼다.
3. 최종 등급 슬라임의 방출 또는 포인트 환원을 추가한다.

# 18. 자동 합성

## 18.1 해금

- 일반 도감 **10종 등록 시 해금**

## 18.2 ON/OFF

```text
자동 합성 [ON / OFF]
```

ON/OFF 상태 저장.

## 18.3 기본 작동

일정 시간마다 필드에서 합성 가능한 **일반 슬라임**을 탐색한다.

한 번의 발동 시 각 레벨별로 최대 N쌍을 합성한다.

### 자동 합성 주기 — 확정

- 기본: **20초**
- 업그레이드당: **-0.5초**
- 최소: **3초**
- 총 속도 업그레이드: **34회**

### 한 번에 합성하는 쌍 수

| 현재 자동 합성 주기 | 각 레벨별 최대 합성 쌍 |
|---:|---:|
| 20초 ~ 10.5초 | **1쌍** |
| 10초 ~ 3.5초 | **2쌍** |
| 3초 | **3쌍** |

```text
3초 상태
Lv.1 × 7

→ Lv.1 + Lv.1 → Lv.2
→ Lv.1 + Lv.1 → Lv.2
→ Lv.1 + Lv.1 → Lv.2
→ Lv.1 1마리 잔여
```

## 18.4 연쇄 합성 금지

한 번의 자동 합성 발동에서 **그 발동으로 새로 만들어진 슬라임은 다시 합성 대상이 되지 않는다.**

발동 시작 시점의 스냅샷/대상 목록을 기준으로 처리한다.

## 18.5 특별 슬라임 보호

특별 슬라임은 자동 합성 대상에서 **완전히 제외**한다.

```text
isSpecial == true
→ AutoMerge candidate 제외
```

일반 + 특별 자동 합성도 없음.

## 18.7 플레이어 조작 보호 — 확정

자동 합성이 플레이어가 다루고 있는 대상을 가져가지 않는다.

**개체 단위 제외**

- 드래그 중인 슬라임은 자동 합성 대상에서 제외한다. 손에 든 슬라임이 사라지지 않는다.

**발동 자체를 정지**

- 장식장 `장식장으로 보내기` 선택 모드(§7.4) 중에는 자동 합성을 멈춘다. 고르려던 슬라임이 없어지지 않게 한다.
- 가챠 연출(§17) 중에도 멈춘다. 연출이 끝나고 결과 슬라임이 놓일 자리가 사라지지 않게 한다.

> 가챠 연출 항목은 앞의 두 결정과 같은 원칙에서 확장한 것이다. 불필요하면 빼도 된다.

정지 중에 흐른 시간은 주기에 누적하지 않는다. 정지가 풀리면 멈춘 지점부터 이어간다.

## 18.6 업그레이드 UI

미래 마일스톤을 미리 크게 알려주지 않는다.

평소:

```text
다음 강화
14.5초 → 14.0초
```

다음 강화가 실제로 10초가 되는 경우에만:

```text
다음 강화
10.5초 → 10.0초
+ 한 번에 합성하는 수 증가
```

최종 3초 직전:

```text
다음 강화
3.5초 → 3.0초
+ 한 번에 합성하는 수 증가
```

`10초 달성 시 ...` 같은 먼 미래 안내는 표시하지 않는다.

- 게임 활성화와 `SpawnManager.Initialized`를 모두 확인한 뒤 시작한다.
  저장 데이터를 읽었다는 사실만으로 화면 개체 복원이 끝났다고 가정하지 않는다.

  대사별 체크포인트는 추가하지 않으며 중간 설명은 다시 나올 수 있다.
- 마지막 대화가 끝나야 완료 플래그를 저장한다. 비정상 중단은 완료로 기록하지 않는다.
- 유치원에 개체가 없을 때 최초 Lv.1을 생성하는 기존 규칙은 유지한다.
  장식장에 이미 있는 슬라임을 대체하거나 다시 보내도록 요구하는 동작은 아니다.

# 22. 저장 데이터 권장 구조

> 아래는 구현 방향 제안이며, 실제 클래스명/구조는 기존 프로젝트를 먼저 분석한 뒤 맞춘다.

## SchemaVersion — 확정

`CurrencySaveData` / `SlimeStatusSaveData` / `UpgradeSaveData` 세 저장 데이터 모두에 `SchemaVersion : int`를 둔다. Phase 1.5에서 함께 넣는다.

# 25. 구현 우선순위

> **출시 방침: 전부 완성한 뒤 출시한다.** Phase 8까지 끝내고 내보내며, 중간 버전을 배포하지 않는다.
>
> 그 결과 각 Phase의 스키마 확장은 **실제 유저 데이터를 건드리지 않는다.** 아래 각 단계의 `세이브 호환` 항목은 신규 필드의 기본값 규칙을 정의한 것이지, 라이브 마이그레이션을 요구하는 것이 아니다. 개발 중 테스트 세이브는 필요하면 지우고 새로 만들어도 된다.

## Phase 1 — 데이터 / 기존 성장 확장

**저장 스키마를 바꾸지 않는 항목만 모은다.** 개체 모델 전환은 위험도와 검증 방법이 달라 Phase 1.5로 분리했다.

1. 기존 슬라임/저장/스폰 구조 분석
2. 자연 스폰 상한 Lv.1~6 구현
3. Weight 기반 스폰 구조 (상한표와 기본 Weight는 ScriptableObject로 분리)
4. Lv.5 상위 슬라임 등장 확률 업그레이드 (최대 Lv.50)
   - Lv.11 / 21 / 31 / 41에서 자연 스폰 Lv.3 / 4 / 5 / 6 구간을 연다.
   - `EUpgradeType`에 새 값은 반드시 `Count` 직전에 덧붙인다. 중간 삽입은 저장된 int 값이 밀려 세이브를 손상시킨다.
   - `SystemUpgradePanel`의 항목 배열이 씬에 직렬화되어 있어 GameScene 편집이 함께 필요하다.
5. 최대 개체 수 상한 확장 — `MaxCountAdd`의 `MaxLevel`을 30에서 40으로 올려 최종 50마리를 만든다.
   - 스테이지 2 해금에 묶는 게이팅은 `UpgradeManager.IsLockedByProgress`에 이미 구현되어 있다.

**완료 기준:** 기존 핵심 루프를 깨지 않고 최고 해금 레벨에 따라 상위 자연 스폰이 정상적으로 변화한다.

**세이브 호환:** 신규 업그레이드 타입이 기존 세이브에서 레벨 0으로 로드된다.

## Phase 1.5 — 슬라임 개체 모델 전환

Phase 2 이후 모든 단계의 전제다. 완료 판정 방법이 Phase 1과 다르므로 단계를 분리한다.

**이 단계의 내부 순서를 지킨다.** 1번을 먼저 하지 않으면 2번 이후의 모든 필드를 세 곳에 중복해서 넣게 된다.

1. **저장 데이터의 중복 기술을 먼저 제거한다** (아래 별도 절)
2. 세 저장 데이터에 `SchemaVersion` 필드를 넣는다 (`CurrencySaveData` / `SlimeStatusSaveData` / `UpgradeSaveData`)
3. `SlimeStatusSaveData.ActiveSlimes`를 `등급 → 개수` 집계에서 개체 리스트로 전환
4. `InstanceId` / `Grade` / `IsSpecial` / `Location` 필드 정의
5. 기존 세이브 승격 규칙 — 저장된 개수만큼 인스턴스를 만들고 `IsSpecial = false`, `Location = MainStage`로 채운다
6. `SlimeController`와 개체의 연결
7. 위치(Position)는 저장하지 않고, 복원 시 현재 공간의 임의 위치에 배치

**완료 기준:** 기존 세이브로 실행했을 때 슬라임 수와 등급이 그대로 복원되고, 앱 재시작을 반복해도 동일하다.

**기존 데이터 처리:** 실제 유저는 없지만(부록 A 10번) **승격 규칙은 작성한다.** 규칙 자체가 `개수 N → 인스턴스 N개`로 단순해 비용이 작고, 개발 중 테스트 세이브를 잃지 않으며, 출시 이후 같은 형태의 스키마 변경이 반복될 때 참고할 첫 사례가 된다.

다만 **출시 전이므로 이 승격이 실패해도 치명적이지 않다.** 막히면 테스트 문서를 지우고 진행해도 되며, 실기기 검증을 착수 조건으로 걸지 않는다.

### 저장 데이터의 중복 기술 제거 — 가장 먼저 한다

현재 저장 데이터 한 종류가 **세 곳에 따로 기술**되어 있다.

```text
SlimeStatusSaveData            Firestore용. 프로퍼티 { get; set; }
SlimeStatusSaveDataWrapper     JsonUtility용. 필드
SlimeManager.SaveCurrentAsync  생성 지점
```

래퍼가 있는 이유는 **`JsonUtility`가 프로퍼티를 직렬화하지 못하기 때문**이다. 필드만 읽는다. 반면 Firestore는 프로퍼티를 요구한다. 그래서 프로퍼티를 필드로 옮겨 담는 래퍼가 따로 존재한다.

그 결과 **필드 하나를 추가할 때마다 3~4곳을 편집**해야 한다. §22 기준으로 앞으로 추가될 필드가 15개를 넘으므로 45번 이상의 중복 편집이 된다. 한 곳을 빠뜨리면 **저장은 되는데 로드에서 조용히 사라지는** 버그가 생기고, 컴파일도 통과하고 에러도 나지 않는다.

**해결책은 이미 프로젝트에 있다.** `com.unity.nuget.newtonsoft-json 3.2.2`가 설치되어 있고, Newtonsoft는 프로퍼티를 직렬화한다.

```csharp
// 지금
var wrapper = new SlimeStatusSaveDataWrapper(saveData);
string json = JsonUtility.ToJson(wrapper);

// 바꾼 뒤
string json = JsonConvert.SerializeObject(saveData);
```

래퍼 클래스 4개(`SlimeStatusSaveDataWrapper`, `SlimeEntryWrapper`, `UpgradeSaveDataWrapper`, `UpgradeEntryWrapper`)를 삭제할 수 있고, 필드 추가 지점이 **3곳에서 1곳**으로 줄어든다.

기존 세이브 JSON과도 호환된다. 래퍼의 필드명과 SaveData의 프로퍼티명이 모두 같기 때문이다.

**확인이 필요한 것:** Newtonsoft는 리플렉션을 사용하므로 Android IL2CPP의 코드 스트리핑에 영향을 받을 수 있다. 패키지에 AOT용 DLL(`Runtime/AOT/Newtonsoft.Json.dll`)이 포함되어 있지만 **실기기 검증 전에는 단정하지 않는다.** 출시 전이라 실패해도 잃을 데이터는 없다.

### `SchemaVersion`을 지금 넣는 이유

출시 전에는 쓸모가 없다. **출시 이후를 위한 것이다.**

버전 필드가 없으면 저장된 데이터가 어느 시점의 모양인지 판단할 근거가 `특정 필드가 있는가 없는가`뿐이다. 스키마가 여러 번 바뀌면 이 추론들이 서로 얽혀, `A 필드는 있는데 B 필드는 없는 세이브`가 정상인지 손상인지 구분할 수 없게 된다.

버전 필드가 있으면 읽을 때 한 번만 분기하면 된다.

```text
if (SchemaVersion < 2) → ...
if (SchemaVersion < 3) → ...
SchemaVersion = 현재값으로 갱신 후 저장
```

비용은 `int` 필드 세 개다. **출시 후에는 넣어도 `버전 없음 = 태초` 예외를 영구히 안고 가야 하므로, 지금이 값싼 유일한 시점이다.**

# 26. Acceptance Criteria / 주요 테스트

## 자연 스폰

- [ ] 최고 Lv.4 이하에서 Lv.2가 자연 스폰되지 않는다.
- [ ] Lv.5에서 Lv.2 자연 스폰이 해금된다.

## 장식장

- [ ] 일반 종류당 1마리 제한.
- [ ] 특별 종류당 별도 1마리 제한.
- [ ] 일반이 있어도 같은 종류 특별 슬라임은 보관 가능.
- [ ] 장식장 개체는 생산/드랍/합성하지 않는다.
- [ ] 메인 필드가 가득 차면 꺼낼 수 없다.
- [ ] 꺼낸 후에도 도감 등록은 유지된다.
- [ ] 넣은 직후 바로 꺼내도 도감 등록이 유지된다. (의도된 동작)
- [ ] 장식장 진입/복귀가 필드 슬라임과 매니저 상태를 초기화하지 않는다.
- [ ] 장식장에 있는 상태로 앱을 재시작하면 메인 스테이지에서 시작한다.
- [ ] 뒤로가기가 관찰 → 정보 UI → 도감 → 장식장 → 업그레이드 패널 → 종료 팝업 순으로 닫힌다.
- [ ] 오프라인 포인트 보상 계산에 장식장 개체가 포함되지 않는다.

## 도감

- [ ] 최초 생성만으로 등록되지 않는다.
- [ ] 장식장에 넣으면 즉시 영구 등록된다.
- [ ] 장식장에서 꺼낸 뒤에도 등록 상태가 유지된다.
- [ ] 자연 스폰·합성 결과·유효 터치·누적 생산 통계가 등급별로 저장된다.
- [ ] 초기 생성·복원·에디터 단축키·오프라인 보상은 통계에서 제외된다.
- [ ] 등록된 항목 상세에 현재 능력과 누적 기록이 표시된다.

## 가챠

- [ ] 슬롯이 가득 차면 가챠 불가.
- [ ] 일반 결과가 최고 해금 레벨을 넘지 않는다.
- [ ] 일반 결과가 최고 해금 레벨 자체를 생성하지 않는다.
- [ ] 특별 결과도 최고 해금 레벨을 넘지 않는다.
- [ ] 특별 결과는 현재 최고 해금 레벨 자체는 가능.
- [ ] 특별 확률/피버 정보를 UI에 표시하지 않는다.

## 자동 합성

- [ ] OFF 상태에서는 절대 실행되지 않는다.
- [ ] 특별 슬라임은 자동 합성되지 않는다.
- [ ] 20~10.5초는 레벨별 1쌍.
- [ ] 10~3.5초는 레벨별 2쌍.
- [ ] 3초는 레벨별 3쌍.
- [ ] 새로 생성된 결과가 같은 Tick에서 다시 합성되지 않는다.
- [ ] 드래그 중인 슬라임은 자동 합성되지 않는다.
- [ ] 장식장 선택 모드와 가챠 연출 중에는 자동 합성이 발동하지 않는다.
- [ ] 정지 중 흐른 시간이 자동 합성 주기에 누적되지 않는다.

## 자동 스폰

- [ ] OFF로 두면 새 슬라임이 생성되지 않는다.
- [ ] OFF 상태에서 합성으로 만든 빈 슬롯이 자동으로 채워지지 않는다.
- [ ] 다시 ON으로 바꾸면 멈춘 지점부터 타이머가 이어진다.
- [ ] ON/OFF 상태가 앱 재시작 후에도 유지된다.
- [ ] 최고 Lv.7 이전에는 노출되지 않는다.

## 티켓 입력

- [ ] 티켓이 슬라임 위에 겹쳐도 슬라임 터치가 가려지지 않는다.
- [ ] 티켓 버튼이 슬라임 터치보다 우선한다.

## 저장

- [ ] 장식장 개체 저장/복원.
- [ ] 일반/특별 도감 저장/복원.
- [ ] 미수령 티켓 저장/복원.
- [ ] 자동 합성 ON/OFF 저장.
- [ ] 피버 누적 상태 저장.
- [ ] 신규 세이브 필드가 기존 유저 데이터 로드를 깨지 않는다.

# 29. Claude / Codex 작업 시작 지침

작업 시작 시 아래 순서를 따른다.

1. 이 문서를 읽는다.
2. 저장소 전체 구조를 먼저 탐색한다.
3. 기존 `Slime`, 스폰, 합성, 업그레이드, 세이브/로드, Firebase/로컬 저장 흐름을 파악한다.
4. 바로 코드를 수정하지 말고 **현재 구조와 착수할 Phase의 적용 계획**을 먼저 작성한다.
5. 기존 아키텍처를 최대한 재사용한다.
6. 새로운 시스템을 넣기 위해 전체 구조를 불필요하게 재작성하지 않는다.
7. 저장 데이터 변경은 항상 기존 세이브 호환성을 검토한다.
8. 한 Phase를 끝내고 테스트한 뒤 다음 Phase로 이동한다.
9. 미확정 밸런스 수치는 하드코딩하지 말고 조절 가능한 데이터로 둔다.
10. 이 문서와 코드가 충돌하는 경우 기존 구현 방식은 존중하되, 게임 규칙은 이 문서의 **확정 항목**을 기준으로 맞춘다.

## 착수 전에 먼저 고쳐야 하는 것

### 1. 재화 배열 로드 가드 (기존 Android 유저 파손 위험)

`CurrencyManager`가 저장된 재화 배열을 길이 검사 없이 읽는다.

```csharp
double[] currencyValues = saveData.Currencies;
for (int i = 0; i < _currencies.Length; i++)
{
    _currencies[i] = currencyValues[i];   // 길이 검사 없음
}
```

`_currencies.Length`는 `ECurrencyType.Count`로 컴파일 시점에 정해지고, Firestore에 저장된 배열은 저장 당시의 길이를 유지한다. 가챠권을 `ECurrencyType`에 추가하면 **기존 Android 유저의 로드가 `IndexOutOfRangeException`으로 실패**한다. 이 예외는 `async UniTaskVoid` 안에서 발생하므로 `OnDataInitialized`가 끝내 발행되지 않고, 게임은 로딩에서 멈춘다.

로컬 경로(`LocalCurrencyRepository`)는 키 단위 `HasKey` 검사가 있어 안전하므로 **에디터에서는 재현되지 않는다.** Android 실기기에서 기존 세이브로만 발생한다.

가챠권을 별도 필드로 두더라도 재화가 늘어나면 같은 문제가 반복되므로, 재화를 추가하기 전에 길이 가드를 먼저 넣는다.

### 2. 무한 업그레이드의 공식 (§4.1)

현재 생산 업그레이드는 **비용이 지수, 효과가 선형**이다.

| 항목 | Lv.20 슬라임 터치 생산 |
|---|---|
| BaseCost | 1,241,049,600 |
| CostMultiplier | 1.5 (레벨당 지수) |
| PointMultiplier | 49,641,984 (레벨당 선형 가산) |

레벨 10에서 20으로 갈 때 비용은 57.7배에서 3,325배로 **57.6배** 오르지만 효과는 **2배**만 오른다. 레벨당 가성비가 1.5배씩 나빠지므로 30레벨 부근에서 사실상 구매 불가가 된다. 즉 지금 공식으로는 `무한 업그레이드`가 성립하지 않고 자연 상한이 생긴다.

`EPointFormula`에 지수 공식을 추가하거나 `CostMultiplier`를 낮춰야 한다. 밸런스 수치가 아니라 **공식 구조**의 문제이므로 §27의 미확정 항목과 별개로 먼저 정해야 한다.

### 3. 숫자 표기 상한

`NumberFormatExtension`의 접미사가 `"", K, M, B, T`까지만 있다. 무한 업그레이드를 도입하면 Lv.20 터치 생산 비용이 40레벨 부근에서 `13725T`, 60레벨 부근에서 `45652035T`로 표시된다. `double` 자체는 여유가 있으므로 한계는 표기 쪽이다. 접미사 확장이나 지수 표기 전환이 함께 필요하다.

### 4. 자동 합성의 저장 묶기

`MergeManager.Merge` 1회마다 `SlimeManager.MergeSlime`이 즉시 저장한다. 자동 합성이 최대 속도(3초 주기, 레벨별 3쌍)에 도달하면 **한 틱에 최대 60회의 저장이 같은 프레임에 몰린다.**

`Documentation/PLAYERPREFS_SAVE_PROFILING.md`의 실기기 측정은 **정상 상태의 호출 빈도**(4.3회/초, 30마리)를 대상으로 했고 그 가설은 기각되었다. 이번 변경은 빈도가 아니라 **분포**를 바꾸므로 그 측정 결과를 그대로 적용할 수 없다.

성능 판단과 별개로, 한 번의 자동 합성 발동에서 60번 저장할 이유가 없다. **발동 단위로 한 번만 저장**하도록 묶는다. 그러면 재측정 자체가 불필요해진다.

### 5. 업그레이드 UI 구조

현재 `UpgradePanel`은 슬라임 업그레이드 40개를 평면으로 생성하며, `Refresh()`가 `_items[i]`와 `upgrades[i]`를 **인덱스로 짝짓는다.** §4.1의 슬라임별 카드 구조로 바꾸려면 이 인덱스 결합을 `(EUpgradeType, ESlimeGrade)` 키 기반으로 먼저 바꿔야 한다.

### 6. 열거형 확장 규칙

`EUpgradeType`과 `ESlimeGrade`는 세이브에 **int 값으로 직렬화**된다. 새 업그레이드 타입은 반드시 `Count` 직전에 덧붙이고, 기존 값 사이에 삽입하지 않는다. 중간 삽입은 저장된 업그레이드 레벨이 다른 항목으로 옮겨 붙는 조용한 세이브 손상을 만든다.

`UpgradeManager`는 세이브에 없는 업그레이드를 레벨 0으로 처리하므로, 끝에 덧붙이는 방식은 기존 세이브와 호환된다.

### Phase 2 — 장식장

Phase 1.5에서 준비된 부분:

- `SlimeInstance`에 `MainStage` / `DisplayRoom` 위치 축이 있다.
- 위치는 DTO, PlayerPrefs와 Firestore에 저장된다.
- v0/v1 저장은 `MainStage`로 승격된다.
- 복원과 오프라인 포인트 계산은 `MainStage` 개체만 사용한다.

Phase 2에서 완료한 부분:

- `SlimeInstance.MoveTo()`를 UI가 직접 호출하지 않고
  `SlimeManager.MoveSlime(instanceId, location)` 경계로 이동·검증·저장을 묶는다.
- 메인 최대 개체 수는 Ground + Sky의 `MainStage` 개체만 세고,
  `DisplayRoom` 개체는 제외한다.
- 장식장용 화면 상태는 `CurrentStage`에 추가하지 않고 별도 런타임 상태로 둔다.
- 기존 `GameExitManager`의 하드코딩된 종료 흐름을 관찰·도감·장식장까지 처리할
  수 있는 닫기 우선순위 스택으로 확장한다.
- 공간 전환 중 월드 입력, 자동 생산, 합성과 스폰의 활성 조건을 한 곳에서
  판정한다.
- Ground / Sky와 분리된 `EGameplaySpace.DisplayRoom` 런타임 상태와 전용
  배경·좌우 전환 연출을 구성했다.
- 메인 스테이지의 보내기 선택 모드에서 터치 생산과 드래그 합성을 막고,
  같은 종류 중복 보관 경고와 연속 입고를 지원한다.
- 장식장 정보 UI에서 이름, 번호, 한 문장 소개, 꺼내기와 메인 필드 용량
  부족 안내를 제공한다.
- Phase 2-B에서 관찰 모드, 전체 화면 복귀 입력, 상·하단 UI 숨김과 카메라
  포커스·추적을 구현했다.
- 장식장 진입 시 슬라임 업그레이드 버튼과 시스템 업그레이드 패널을 화면
  밖으로 이동시켜 전시 공간을 가리지 않게 했다.

### Phase 3 — 도감

도감 등록 데이터와 누적 통계는 `SlimeStatus`가 소유한다. 장식장 현재 보관 상태와
영구 도감 등록 상태를 분리하고, 일반 등록 이벤트와 등록 수 변경 이벤트를 최초
등록 때 한 번만 발행한다. 장식장 입고와 기존 장식장 개체 복원 시 자동 등록하며,
꺼낸 뒤에도 기록을 유지한다.

메인 스테이지·장식장 공통 `CollectionButton`, 일반 20종의 2개 단위 페이지,
미등록 표시, 상세 정보와 모션 미리보기를 구현했다. 최초 등록일·자연 출현·합성
탄생·유효 터치·누적 생산량은 등급별로 저장한다. 특별 등록 상태와 이벤트는
Phase 5에서 같은 경계로 확장한다.

### Phase 4 — 가챠권

아래 네 항목은 구현 전에 반드시 결정한다.

1. 보유 티켓을 `ECurrencyType`에 추가할지 별도 저장 데이터로 둘지
2. 미수령 티켓 개체의 최소 필드
   (`TicketId`, 소속 Ground/Sky, 화면 위치 또는 복원 위치 규칙)
3. 60초 판정을 전역 Tick으로 할지 개체별 생존 시간으로 할지
4. 미수령 티켓의 최대 개수와 상한 도달 시 처리

티켓을 `ECurrencyType`에 추가하면 `CurrencyManager`의 배열 길이 가드를 먼저
구현해야 한다. 별도 필드로 두더라도 앱 종료 직전 드랍과 수집이 중복 또는
소실되지 않도록 ID 기반 복원 규칙이 필요하다.

### Phase 5 — 가챠와 특별 슬라임

- `티켓 1장 소비 → 결과 결정 → SlimeInstance 생성 → 저장` 사이에 앱이
  종료되어도 티켓만 사라지거나 결과가 중복되지 않는 복구 규칙이 필요하다.
  최소 구현은 확정된 결과를 `PendingGachaResult`로 먼저 저장하고, 필드 생성
  완료 후 제거하는 방식이다.
- 자연 스폰과 가챠가 최고 해금 등급을 올리지 않도록 최고 등급 갱신을
  합성 경로에서만 호출하게 정리한다.
- `IsSpecial`만으로는 표현이 끝나지 않으므로 등급별 특별 비주얼과
  `SlimeController`/애니메이터 연결, 누락 에셋 폴백을 Phase 완료 범위에 넣는다.
- 가챠 결과가 속한 Ground/Sky가 현재 화면과 다를 때의 이동 연출과 입력 잠금도
  완료 기준에 포함한다.

### Phase 6 — 자동 합성

- 발동 시작 시 개체 스냅샷을 만들고 ID로 대상을 고정한다.
- 한 Tick의 모든 합성을 도메인에서 배치 처리한 뒤 저장은 한 번만 수행한다.
- 합성별 연출·해금 이벤트와 최종 최고 등급 갱신은 유지하되 저장 호출과
  분리한다.
- 자동 합성 ON 상태에서 Phase 4 드랍 대상과 Phase 5 빈 슬롯 판정을 다시
  검증한다.

### Phase 7 — 도감 마일스톤

- 해금 여부를 중복 저장하기보다 영구 도감 등록 수에서 재계산할 수 있는 값과
  별도 저장해야 하는 값(ON/OFF, 피버 실패 횟수, 엔딩 확인)을 구분한다.
- 오프라인 티켓은 필드 오브젝트가 아니라 보유 티켓으로 직접 정산할지
  명시한다.
- 현재 오프라인 시간은 기기 UTC 기준이다. 경쟁·랭킹·유료 재화와 연결하기
  전까지는 유지할 수 있지만, 연결 시 서버 권위 시간이 필요하다.

### Phase 8 — UX / QA / 출시

기존 체크리스트에 다음을 추가한다.

- Editor Play Mode와 Android 개발 빌드, Release AAB를 분리해 기록
- Google Play Games 로그인 실패·재시도와 Firebase Auth 세션 확인

- Play Console 서명, 내부 테스트 설치와 크래시 심볼 확인

  위로 이동하는 슬라이드 연출이며 이동 메뉴는 캐러셀이 아닌 버튼 모음이다.
- 이동 메뉴에는 스테이지 이동·장식장 이동·장식장으로 보내기 버튼을 모았다.
  장식장에서는 복귀용 이동 패널을 유지하며 관찰 모드에서는 하단 HUD와 함께 숨긴다.

  버튼의 라벨·클릭 전달은 `SpaceToggleButtonUI`가 맡는다. `DisplayRoomUI`가
  공간 전환과 보내기 모드를 연결하며 튜토리얼도 공간 버튼의 명시적 참조를 사용한다.
- 상하단 HUD 루트의 위치는 `HudVisibility`가 단독으로 소유한다. 보내기 모드는
  `Top`, 관찰 모드는 `All`을 요청하며 요청은 소유자별로 쌓여 합집합만큼 숨긴다.
  시작 위치를 아는 곳이 하나뿐이라 두 연출이 겹쳐도 HUD가 화면 밖에 남지 않는다.
- 하단 패널은 `BottomPanelSwitcher`가 활성 상태로 감추므로 HUD 요청 대상이
  아니다. 업그레이드 서랍도 자기 폭과 Safe Area로 숨김 위치를 계산하므로
  `UpgradeUI.SetToggleVisible()`에 맡기고 좌표를 직접 옮기지 않는다.
- 장식장 입·출고의 완료 처리는 `StageManager.TryRelocateSlime()` 하나로 모았다.
  저장 위치 변경·좌표 재배치·표시 갱신·실패 시 원복이 여기 있고, 토스트 문구와
  후속 UI 동작만 호출부에 남는다.

  공간 기본값보다 튜토리얼 대상 제한, 그보다 팝업·연출 차단이 우선한다.

  우선한다. 기존 `SetInputMode`와 전역 `TutorialManager.IsRunning` 가드는 제거했다.
- 정보창 입력 잠금은 카메라 복귀 완료 후 해제한다. 공간 전환으로 복귀 연출이
  취소되더라도 `ForceClose()`가 표시 여부와 관계없이 자기 요청을 해제한다.
- 보내기 종료 시 업그레이드 열기 버튼을 진입 전 상태로 복구해 일반 플레이에서는
  다시 열리고, 튜토리얼이 이미 잠가둔 경우에는 잠금이 유지된다.
- Safe Area 계산을 공용 유틸리티로 통합하고, 주요 팝업의 CanvasGroup과
  AudioSource를 씬에 미리 구성했다.
- 튜토리얼 전용 프레젠테이션을 공용 `DialoguePresentation`으로 확장했다.
- 실행 관리는 `TutorialManager`에 남기고 메인·상위 자연 스폰·장식장 진행은
  각 `TutorialSequence` 컴포넌트로 분리했다.
- Lv.3 해금 연출 뒤 하단 메뉴 전환, 입고 모드, 지정 슬라임 1마리 전송, 장식장
  진입, 정보 영역 강조, 관찰·꺼내기 설명과 닫기까지 수행하는 1회성 튜토리얼을 연결했다.
- 장식장의 종류별 1마리 제한, 유치원 정원에 따른 꺼내기 제한과 장식장
  슬라임의 포인트 생산 제외 규칙도 안내한다.
- 재실행 시 화면 개체 복원 전에 입고 여부를 판단하던 순서를 수정했다.
  이미 장식장에 보낸 슬라임이 있으면 입고를 반복하지 않고 안내를 재개한다.
- 상위 스폰 튜토리얼은 캐러셀 선택뿐 아니라 시스템 업그레이드 패널 표시도
  먼저 확정한다. 패널 전환 중이어도 전환 상태를 정리한 뒤 버튼을 강조한다.

### 옵션과 진행도 초기화

- 우측 상단 옵션 버튼, 음량 슬라이더와 초기화 확인창을 씬에 미리 구성했다.
- `AudioManager`가 배경음·효과음 값을 기기별 PlayerPrefs에 저장한다.
  BGM 크로스페이드 가중치와 사용자 음량을 구분하고 SFX 음량 중복 적용을 정리했다.
- `GameDataResetService`가 현재 계정의 재화·슬라임·업그레이드와 이 기기의
  튜토리얼 완료 기록을 삭제한다. Android는 해당 UID의 Firestore 문서 3개도
  삭제하고, Editor는 로컬 저장만 삭제한다. 인증 계정과 음량 설정은 유지한다.
- 초기화 중 진행·저장을 잠그고, 이전 세대의 지연 저장을 폐기한다. 이미 전송된
  Firestore 쓰기를 기다린 뒤 삭제하며 완료 후 로그인 화면으로 돌아간다.
- 중단 표시를 로컬에 남겨 다음 로그인에서 초기화를 마무리한다. 타임아웃은
  서버 작업 취소를 보장하지 않으므로 결과가 불명확하면 기존 게임에 복귀하지 않는다.
- 2026-08-29 옵션에 별도 계정 삭제를 추가했다. 현재 UID의 게임 데이터를 먼저
  정리한 뒤 Firebase 인증 계정을 삭제하며, 중단 표시는 다음 로그인에서 삭제를
  재개한다. Google 계정과 Play 게임 프로필, 기기별 음량 설정은 유지한다.
- **다기기 제한:** 다른 기기의 로컬 저장은 무효화하지 않는다. 해당 기기로
  접속하면 이전 진행도가 다시 저장될 수 있으며 계정 단위 초기화 세대 관리는 미구현이다.

## Phase 2-B — 완료

### 정보와 관찰

- 장식장 슬라임을 선택하면 카메라가 해당 개체를 중앙에 두고 확대한다.
- 정보 UI에 이름, `No.`, 등급별 한 문장 소개를 표시한다.

  전달하지 않는다.

- 선택 개체에만 `Rigidbody2D.Interpolate`를 적용하고 카메라 위치를
  `LateUpdate`에서 보간된 위치로 추적한다.
- 정보 보기와 관찰의 확대 단계를 분리하고, 종료 시 카메라 위치·확대율과
